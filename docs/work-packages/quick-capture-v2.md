# Quick Capture V2 work package

Baseline: `ec5e4f811805daaa485ffaa8dede42f344761e13`, tag `release-20260927-181500`. The working tree was clean; the online `admin.html` and 27 CRM Functions (115 source/config files) matched local in the pre-change cloud check. GitHub was verified at the prior release and at the start of this work, while one additional `ls-remote` attempt failed due to a local proxy connection; release verification must recheck GitHub.

Scope: `quick_capture_v2` is false by default in the current CRM host. The legacy Quick Capture button, `ai_parse.quick_capture` request/response and its customer/recruit/speaker/followup save path remain unchanged. When explicitly enabled, a separate modular V2 button calls the same `ai_parse` action with `version: 2` and opens an editable preview. The parser uses the configured CloudBase model through the existing function helper and performs no database write. The browser calls the authenticated `person_360` function to run `PersonService.resolveName()`; it cannot auto-select or create a Person. Confirmation re-resolves the selected Person server-side.

The V2 confirmation RPC is `public.quick_capture_v2_commit`, created by `cloudbase/migrations/20260927145526_quick_capture_commit.sql` with guarded rollback at `cloudbase/rollbacks/20260927145526_quick_capture_commit.sql`. It is `SECURITY INVOKER`, executable only by `service_role`, and atomically inserts one `public.interactions` row plus the retained Fact and Signal candidates into `public.context_items`. The Context Items retain AI provenance and `confirmed=false`. Opportunity, Action and Commitment candidates are preview-only by the accepted first-stage scope. The migration was backed up to the documented second migration directory with equal SHA-256 content. Task `task-b27dea18` succeeded and the migration appeared in remote history.

Validation: `tests/quick-capture-v2/validate-transaction.sql` used one marked Person fixture inside a rolled-back subtransaction. It checked a valid two-candidate write, exact-name rejection, invalid-candidate rejection, and no partial rows after rejected writes. A read-only check after execution found zero marked Persons, Interactions or Context Items. The function ACL check found `anon=false`, `authenticated=false`, `service_role=true`. Offline V2 server tests passed 5/5; PersonService tests 6/6; Person 360 tests 5/5; modular frontend check passed. The browser test exercised the flag-enabled preview, blocked write without explicit Person selection, accepted a manually edited Fact, and verified that no Opportunity or Followup create was called. The final full offline regression passed 61, failed 0, skipped 5; browser regression passed 33, failed 0, skipped 6. A first sandboxed repeat had only a browser debugger startup failure; rerunning in the permitted browser environment passed without changing business code. After deploying the two affected functions, live negative-path calls confirmed V2 rejects empty input, legacy Quick Capture retains its empty-input response, and unauthenticated V2 commit is rejected. The three individually deployed static files (`admin.html`, the V2 module and its CSS) matched the online files byte for byte. The full post-deploy CLI source check passed: 27 functions and 116 source/config files matched local.

Rollout and limits: the flag remains off in production. No real customer data was used for write testing, and no real AI generation was invoked in regression. The required CloudBase AI preflight found `EnvPostpayPackageInfoList=[]` for the production environment, so positive live model generation cannot be validated until an active Token Credits resource pack is available. An authenticated end-to-end V2 write was not run; only the transaction was tested with isolated records and rolled back. A network timeout after confirmation could leave the write result unknown; the UI does not retry automatically and tells the user to check Person 360 before another submission. This stage does not create Persons, promote AI Fact Candidates to confirmed Facts, persist Opportunity/Action/Commitment candidates, or materialize legacy followups. Future rollout should enable the flag only after an active AI package and a real-login pilot of the intended flow.
