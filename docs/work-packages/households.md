# Households and Person 360

Baseline before this package: local and GitHub `master` at `642b93eca401c1118ce6b4dbf4c43e7a7347aa54`, tag `release-20260926-120000`, clean working tree. The online admin page and 26 CRM Cloud Functions (108 source/config files) matched local sources. `public.persons` existed; `public.households` and `public.household_members` did not. No Person 360 route existed.

The additive migration `cloudbase/migrations/20260926005527_households.sql` was planned and applied through CloudBase migration history. Its paired rollback is `cloudbase/rollbacks/20260926005527_households.sql`. It adds two service-role-only RLS tables, two active uniqueness rules, and Person foreign keys. No existing data was changed or inferred. The read-only `tests/households/verify-public.sql` returned zero households, zero members and orphans, RLS enabled, denied `anon`/`authenticated` SELECT, granted `service_role` SELECT, and both active uniqueness indexes present.

The user approved an independent Person 360 entry and specifically authorized a server-only API Key for the new function. The `person_360` Event Function uses it only after `app.auth().getUserInfo()` returns a caller UID. The key is held in that function's `CRM_PERSON360_DB_API_KEY` configuration, not in the repository or browser; it expires on 2026-12-25 and must be rotated before then. The existing gateway policy denies anonymous Cloud Function calls. The function uses fixed public-table and column allowlists; errors never echo the key, runtime environment or arbitrary request metadata. The page uses the existing `callFn` entry. No Person is created automatically, and no wealth-management features were added.

Verification: `tests/households/person360-service.cjs` passed 5 isolated cases; a manually logged-in test account called the deployed function read-only and received an existing Person with zero household/member rows and no error, without saving their name or family data. The full CRM fixture regression passed 60, failed 0, skipped 5, including the new route, member search and populated family display. The real add/remove/save path was not exercised against production because no marked test family record exists; no real family data was modified.

The only newly deployed CRM Function is `person_360`. Static hosting received only `crm/admin.html`, `crm/js/modules/person-360.js`, and `crm/css/person-360.css`; each returned HTTP 200 with a SHA-256 matching its local release file. The database migration added only the two named `public` tables. Existing CRM Functions and routes were retained.

The initial `persons` migration is a snapshot, not a customer synchronization process. A customer created afterward with no Person mapping will see a clear Person 360 unavailable message; this package does not create a Person behind the user's back. Independent Persons can use the new route by ID, but no general Person directory is added here.
