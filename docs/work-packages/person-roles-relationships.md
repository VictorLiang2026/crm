# Person roles and directed relationships

This work package adds `public.person_roles` and `public.relationships` as an additive identity layer. The user chose a directed Person-to-Person relationship (`from_person_id` → `to_person_id`). Existing customer, recruit and speaker stages, Cloud Functions and routes retain their current behavior.

Migrations: `cloudbase/migrations/20260925235318_person_roles.sql` and `cloudbase/migrations/20260925235929_relationships.sql`. Manual guarded rollbacks: matching files in `cloudbase/rollbacks/`. Both migrations were planned, dry-run and applied in order to production CloudBase `crm-d1gkae8ddc930d151`; they only touch `public` objects.

At application, role backfill produced 792 records: 776 customer, 12 recruit, 3 speaker and 1 participant. These are a one-time snapshot from explicit legacy customer IDs, not a live sync. Other supported roles had no evidence-based backfill. Relationships started with zero rows; no relationship was inferred from names or historic stages.

The read-only catalog check confirmed both tables and expected constraints/indexes, RLS enabled, `anon` and `authenticated` SELECT denied, and `service_role` SELECT granted. The read-only `tests/person-relationships/verify-public.sql` returned 792 roles, zero orphans, zero relationships, a valid directed active key, and all three legacy stage columns present. No production test record was written.

The existing regression suite passed 57 cases, failed 0 and skipped 5. The first run could not start the local browser debugger inside the sandbox; a rerun with browser access passed. `npm run check:shared` passed for all 52 shared copies. No page or Cloud Function artifact changed, so no cloud artifact was deployed in this work package. For runtime usage, a future work package must define controlled writes, role synchronization where desired, and relationship vocabularies before enabling any page or function consumer.

## PMC-15 governance update (2026-10-09)

PMC-15 turned the one-time role snapshot into a governed combination catalog and added relationship confirmation gates. Migration: `cloudbase/migrations/20261009220000_pmc15_role_derivation_relationship_governance.sql` with a guarded rollback in `cloudbase/rollbacks/`.

- **Roles = combination with explicit origins.** `customer`/`recruit`/`speaker`/`participant` are derived facts: the SECURITY DEFINER function `crm_person_roles_derive_v1(p_person_id)` recomputes one person's roles from live, non-deleted business rows (customer evidence accepts both the direct `customers.person_id` link and the `persons.legacy_customer_id` bridge; participant evidence uses `canonical_person_id`). Five AFTER triggers on customers, recruit_candidates, activity_speakers, activity_participants and persons invoke `crm_person_role_sync_v1()` on identity/deletion changes. Derived rows carry `origin='derived'`; historical `legacy_backfill` and `manual` rows are untouched. `partner`/`referrer`/`alumni`/`other` remain human-only tags and are never recomputed. Business stages and validity always come from the owning business table; `person_roles` answers only "which active business identities does this person currently hold".
- **Relationship governance.** `relationships` gained `source ∈ {manual, ai_suggested, legacy_note}` (default manual), `status ∈ {pending, confirmed}` (default pending), `confirmed_at` and `confirmed_by_uid`, with CHECK constraints enforcing pending = no confirmation metadata and confirmed = both fields present. `relationship_type` is constrained to `{family, friend, colleague, business, referral, other}`; household vocabulary (spouse/child/parent/sibling) and insurance roles (policyholder/insured) are explicitly excluded. The from→to direction, the partial unique key `(from,to,type) WHERE deleted_at IS NULL`, the self-relationship ban and reverse-edge independence are retained; soft-deleting an edge frees the slot for later re-creation.
- **Confirmation gate.** AI suggestions and clues found in legacy fields or notes may only produce pending candidates; nothing auto-promotes an edge to confirmed, and no application-layer relationship write path exists yet. AI/search/prep consumers (`crm_search_people_v1`, both context-engine copies, person_360 meeting prep) read only confirmed edges.
- **One-time reconciliation.** Two stale snapshot rows were deleted (id 703: customer on soft-deleted person 768; id 792: participant on person 773) and person 777 received the two missing derived roles (customer/recruit), inside an assertion-guarded DO block. Post-checks: 799 roles, zero stale/missing/orphan roles, five sync triggers, zero relationships, zero test residue.
- **Deployed scope:** migration/rollback (public only), functions `ai_activity` and `person_360`, four static modules (person-profile, i18n, console people page, phase14-hubs). Households behavior is unchanged (confirm metadata already existed; COMMENTs added). Evidence: `specs/person-centered-migration/evidence/PMC-15.md`.
