# WP 13.3 · 增员月度目标的事务保存与幂等

## 范围与基线

- 修改前提交 `940012cef216e02f18b1d2d628285f46ea16331b`，回滚代码标签 `release-20261002-011500`。修改前本地、GitHub `master`、线上页面与 28 个 CRM 云函数一致。
- 线上 `public.recruit_goals` 有 14 行。`recruit_goals.saveGoals` 原先先发一次 `DELETE`，再发一次 `INSERT`；第二次请求失败会留下空月份，重复保存会重建行。现有 `(goal_month, stage)` 唯一约束、RLS、表授权和旧页面均保留。
- 本包只处理 `saveGoals`。`listGoals`、`getProgress`、`saveBenchmarks`、其他增员/活动/AI 写入路径不改。

## 实现与兼容

- 新增 `public.crm_recruit_goals_save_v1(text,jsonb,text)`，由旧 `saveGoals` 云函数调用。数据库先验证输入，再按月份取得事务级锁，在同一语句事务内删除本次不再需要的阶段，并对非零目标做条件 upsert。任一步失败则本次保存整体回滚；同月并发调用不会拼出两份请求的混合结果。
- 与旧页面保持 `{ok:true, inserted:<非零阶段数>}` 返回；全零仍清空该月。云函数沿用旧 `parseInt` 归一化方式，未知阶段不写入。相同内容重试时，已有行的 `id`、`created_at`、`updated_at` 不变；保留已有行的 `note`，避免反复保存擦除人工备注。
- 函数为 `SECURITY INVOKER`，仅 `anon` 与 `service_role` 有执行权，`authenticated` 无执行权；不改既有表授权或 RLS。匿名云函数仍受原表的权限边界约束。
- 迁移：[20261002100000_recruit_goals_atomic_save.sql](../../cloudbase/migrations/20261002100000_recruit_goals_atomic_save.sql)；回滚：[同名 rollback](../../cloudbase/rollbacks/20261002100000_recruit_goals_atomic_save.sql)。回滚时先恢复旧 `recruit_goals` 云函数代码，再删除新 RPC，否则新函数会调用缺失的入口。回滚不改业务数据。

## 验证

- 迁移预检仅一条待执行版本，线上任务 `task-3d705903` 成功。权限读回：`SECURITY INVOKER`，`anon=true`、`authenticated=false`、`service_role=true`。
- `[CRM_TEST_ONLY]` 隔离 SQL 用空的 `2099-01` 月份检查首次保存、相同请求无行更新、阶段替换、错误输入无副作用、全零清空和强制回滚；全部通过，测试月份最终 0 行，线上原有目标仍为 14 行。
- 云函数本地针对性测试 3/3 通过，确认保存只发一次 RPC、保留返回形态及失败不退回直接写表。完整隔离回归 90 项通过、0 项失败、5 项预设跳过，覆盖登录、客户、跟进、机会、Today、活动、增员与回收站。
- 仅部署 `recruit_goals` 函数。线上只读 `listGoals` 返回测试月份空列表；线上 `saveGoals` 对空月份提交全零目标返回 `{ok:true,inserted:0}`，随后读回仍为 0 行且全表保持 14 行。正数保存只在会自动回滚的数据库隔离测试中验证，未对真实业务月份写入。

## 剩余风险与后续清单

- 事务锁只序列化经新 RPC 的同月保存；绕过该入口直接写表的调用不受它协调。不同内容的先后保存仍采用最后一次成功提交为准，未解决用户基于旧页面内容覆盖较新修改的问题。跨另一次不同保存之后再重试旧内容，也无法在没有请求标识的旧 API 中识别为过期重试。
- 其他多步骤写入仍需独立工作包评估：`recruit_candidates.create/update` 的候选人与里程碑、`activities.remove` 的活动与参与者、`recruit_goals.saveBenchmarks` 的多行更新、`activity_speakers.create` 的客户与嘉宾，以及 AI Gateway 的跨表审计写入。本轮未修改它们。
