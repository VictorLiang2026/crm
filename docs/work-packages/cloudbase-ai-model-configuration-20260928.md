# CloudBase-managed AI model configuration (2026-09-28)

Baseline: local and GitHub `master` were `d3c99499158fc8663f04b2f5f81471adc44d0262` (`release-20260928-061119`); the working tree was clean. The online page and all 27 CRM functions (116 source/config files) matched local before the change. Only the production environment `crm-d1gkae8ddc930d151` was inspected or configured. No database object, business source file, route, or feature flag changed.

Decision: use CloudBase's managed `cloudbase` model group for the present phase. The current shared `db.js` already reads each function's `AI_MODEL` environment variable and defaults to `hy3`; the AI Gateway also reads environment configuration. The CloudBase SDK still requires a model ID in each request: merely enabling a model in the console does not supply a default ID. A program-side model chooser is deferred. Existing text AI functions currently have `AI_MODEL=hy3` or use the `hy3` fallback. `quick_capture_v2` remains disabled.

Configuration before: the managed `cloudbase` group had `Status=1` and no enabled models. `ai_parse` had three environment variables: `AI_MODEL=hy3`, `TCB_ENV=crm-d1gkae8ddc930d151`, `VISION_MODEL=hy3`. The last setting was unsuitable for the image path because `hy3` does not process image inputs. The environment uses resource-point billing (`EnvDeductionMode=credits`); the personal plan catalog lists 40,000 points per cycle and the current-cycle usage query returned 2,766.46 points. An empty legacy Token Credits pack list does not imply that this resource-point plan cannot call models.

Applied: enabled only `hy3` in the managed `cloudbase` group. A request to enable `hy3` plus the catalog-listed `glm-5v-turbo` was rejected with `当前环境的套餐不支持，请升级到标准版及以上套餐`; the group remained unchanged after that rejection. A separate `hy3` request succeeded. Updated only `ai_parse` function configuration so `VISION_MODEL=glm-5v-turbo`, preserving `AI_MODEL=hy3`, `TCB_ENV`, Node runtime, and timeout. The vision setting names the model the existing image path expects, but it is **not enabled** and image parsing remains unavailable on the current plan. This makes image requests fail explicitly instead of silently passing images to text-only `hy3`. No paid plan upgrade was attempted.

Verification: after the change, `DescribeAIModels` showed `cloudbase` enabled with exactly `hy3`; `ai_parse` still had exactly the same three environment-variable keys and its `VISION_MODEL` was `glm-5v-turbo`. A synthetic, non-customer Quick Capture V2 request returned an editable preview; a separate synthetic legacy Quick Capture request returned `parsed` with no matched person. A one-pixel synthetic image returned `AI_MODEL_NOT_SUPPORTED` and no parsed customer data. These invocations did not write CRM records. Full offline regression: 61 passed, 0 failed, 5 skipped (real-account, production write, mobile, and other live checks covered separately). Production model calls consume resource points; usage reporting may lag.

Rollback: first read the current `cloudbase` enabled-model list and `ai_parse` function configuration again. If no other operator has changed them, restore the previous empty text-model list and `VISION_MODEL=hy3`, preserving all other function variables. This restores the prior unavailable text-AI state and prior image configuration; do not silently roll back customer data. No database migration or rollback applies because no database schema or data changed.

Open limit: the personal plan rejected the selected vision model. Enabling `glm-5v-turbo` would require a separately approved plan change or a different explicitly approved supported vision model. Do not claim image parsing works yet. Future model changes still require CloudBase function environment configuration because the SDK request needs an explicit model ID; this work does not implement a model-selection UI or automatic model discovery.
