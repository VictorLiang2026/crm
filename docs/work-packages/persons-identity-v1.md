# `public.persons` identity foundation

Migration `20260925161449_create_persons_identity.sql` adds `public.persons` without changing `public.customers`, its `"Id"` primary key, its `customer_name` unique constraint, any view, Cloud Function or route. The migration ran against production CloudBase `crm-d1gkae8ddc930d151` on 2026-09-26 local time. The preceding baseline matched local commit `c7042d12f05a730c5385c5276be30089abf59f03`, GitHub and all 26 deployed CRM function sources.

The table has a generated bigint `id`, nonempty `display_name` and `name_key`, optional contact/profile columns, nullable unique `legacy_customer_id`, timestamps and `deleted_at`. `name_key` is lowercase and whitespace-normalized; it is indexed but deliberately not unique. Existing customer values map 1:1: `customer_name` → `display_name`, `wx_account` → `wechat`, `additional_info` → `notes`; phone, gender, birthday, occupation, education, source, creation/update times and deletion state are preserved. `organization` remains null because there is no authoritative customer column for it. `deleted_at` uses the same timestamp type as `customers.deleted_at` to preserve the legacy value exactly. No foreign key or customer trigger was added, so old customer writes keep their current behavior.

`persons` contains personal data but has no runtime consumer yet. RLS is enabled; only `service_role` has table/identity-sequence access and an allow policy. `anon` and `authenticated` grants are revoked. A later caller needs its own permission review. The backfill is repeatable: `CREATE TABLE/INDEX IF NOT EXISTS`, an exact column/unique-constraint guard, conditional policy creation and `INSERT ... ON CONFLICT (legacy_customer_id) DO NOTHING`. A customer table lock and missing-link assertion make the initial 1:1 snapshot atomic. This is **initial backfill only**: new or edited customers will not automatically sync to persons until a separate, reviewed work package adds a write path.

The paired rollback refuses to drop the new table if it contains independent records, misses a customer, or any imported value differs from the current customer value; `DROP TABLE ... RESTRICT` also blocks dependent objects. It is not run automatically. Once a later feature starts editing persons, the rollback must be reassessed rather than forced.

Post-migration read-only verification with `tests/persons/verify-public.sql`: 776 customers, 776 persons, 776 linked persons, 0 missing links, 0 orphan links, 0 field mismatches, 1 copied soft-deleted row; RLS enabled; `anon`/`authenticated` SELECT false and `service_role` SELECT true. Live catalog checks confirmed the new unique key and that the existing customer primary key and name unique constraint remain present. No real customer was modified or deleted.

The existing CRM regression passed 57 cases, with 0 failures and 5 expected skips, including login, customer list/detail, followups, opportunities, activities, recruitment and recycle bin. No page or Cloud Function artifact changed in this release.
