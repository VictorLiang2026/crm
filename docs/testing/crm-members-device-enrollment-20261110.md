# CRM 成员和设备：后台登记与首台设备申请

此工作包提供成员名单、设备申请和后台批准。批准针对「一个成员 + 一个浏览器密钥」。申请入口上线与全站强制拦截是两个不同的切换步骤；只有完成业务函数、附件和独立 GPT 回归后才能宣布整站受保护。

**操作人员**：CloudBase 管理员进入生产环境 PostgreSQL 的 SQL 控制台。CRM 登录账号、报名客户、GPT 工具均没有成员管理或设备批准接口。使用已核对的 CloudBase UID，不按昵称授权。

1. 成员首次登记：在身份认证的用户列表核对账号和 UID 后，执行 `INSERT INTO public.crm_access_members(uid) VALUES ('已核对的UID');`。现有 victor、prtest 已登记，不需要重复执行。
2. 成员在自己的浏览器打开 [设备申请页](https://crm-d1gkae8ddc930d151-1434199662.tcloudbaseapp.com/crm/device-access.html)，用本人账号登录，填写设备备注并申请。私钥留在本浏览器，备注只是方便辨认；审批不能只看备注。
3. 后台查看申请：`SELECT uid,label,fingerprint,state FROM public.crm_browser_devices WHERE state='pending' ORDER BY requested_at DESC;`。当面或通过独立渠道核对成员及页面显示的**完整**设备码。只批准本人确认的那一条：

```sql
UPDATE public.crm_browser_devices SET state='approved'
WHERE uid='已核对的UID'
  AND fingerprint=lower(regexp_replace('完整设备码','[[:space:]]','','g'))
  AND state='pending'
RETURNING uid,label,state;
```

4. 撤销单台设备：相同 UID、完整指纹条件，改为 `SET state='revoked'`，核对返回一行。停用成员：`UPDATE public.crm_access_members SET enabled=false WHERE uid='已核对的UID' RETURNING uid,enabled;`；无需删除 CloudBase 账号。停用会同时撤销该成员设备和未用的挑战，不影响另一人。重新启用不会恢复旧设备；需要使用新浏览器密钥重新申请。尚未接入设备校验的旧接口不能以这一步作为访问已被全面阻断的证据。

初始名单两个账号都是 CRM 业务成员；没有设备被系统预先批准。工作区 `public` 以外的表没有在此工作包修改。报名仍是隔离的访客流程；GPT 连接单独授权，不因成为成员而取得。

## 本次发布的验收记录

- 生产实名账号核对：两个用户名各对应不同的 CloudBase UID，名单中启用人数为 2。设备申请与批准数最初均为 0；未使用两人的密码、未代替本人签发设备。
- 生产页面：全新桌面浏览器通过托管域名提示后看到中文登录表单，看不到设备申请面板；这不是 iPad 真机验收。
- 新成员表、设备表、挑战表的公开密钥直读均返回 401；公开客户端不能通过新 RPC 登记或批准设备。隔离库用合成人员测试了批准、单次挑战、防重放、撤销、停用后重新启用不恢复旧设备，以及一个成员停用不影响另一个。浏览器测试覆盖了签名校验、重载保留密钥、清理站点数据后换钥。
- 现有 GPT 连接：只读调用一条已核对不存在的知识记录，返回 `CONTENT_NOT_FOUND`，未读取真实资料、未写入数据。这只能证明现有连接仍可调用，不能证明其他 ChatGPT 账号均被拒绝。
- 本轮发布数据库迁移及回滚文件、人物服务的申请/挑战入口、独立申请页、样式和双语文本；没有启用旧业务强制设备校验，也没有改变两只文件桶、报名接口或 GPT 授权策略。

## 下一步切换顺序和通过条件

| 步骤 | 落点 | 何时算通过 |
| --- | --- | --- |
| 1. 首台真机 | 在成员实际使用的浏览器申请；后台独立核对完整设备码。不同账号分别批准，不因同一台硬件共用批准。 | 至少一台已批准的真机可以拿到挑战并签名；同密码的新浏览器、其他账号和伪造设备码不能通过。清除浏览器数据需重新申请。 |
| 2. 新旧 CRM | 旧管理页、新工作区和 OAuth 同意页分别有调用入口；服务端在读写业务前校验实际身份、成员启用状态、设备状态和针对本次请求的签名。内部服务调用和定时任务另行验证调用者与操作范围，不能信任事件里自报的来源。 | 直接调用 API 和通过页面都执行同一检查；以合成资料回归人物、客户、跟进、增员、活动和回收站。撤销后用不退出登录的旧浏览器再访问，也被拒绝。 |
| 3. 文件与直接数据访问 | 核查公开密钥、匿名会话、普通账号对业务表、视图和函数的直连；替换旧管理页和新工作区对 recruit、knowledge 的直连。服务端核实设备和附件所属记录后提供文件。 | 直接读取、上传、删除均不能绕过；专门测试以前签发的链接。旧招募链接代码有效期为 1 小时，须验证链接已失效或等待旧链接到期后才能宣称即时撤销覆盖附件。已下载的副本无法远程收回。 |
| 4. 活动报名 | 活动公开说明不含 CRM 资料。报名者使用报名模块的独立凭证；服务端按本次活动及报名人限定可读写范围，不接受猜测编号或姓名作为身份证明。 | 两名合成报名者互换链接参数不能读取或修改对方报名；不能进入管理端或查询 Person。现有报名草稿与 CRM 成员、设备审批不共用权限。 |
| 5. GPT | 保留现有授权。将新建/更换 GPT 连接的权力与普通成员权限分离；限定本人批准的授权，限制回调地址、读写范围及可用令牌；最后再验证撤销。 | 验证已授权连接继续工作，其他 CRM 成员不能借同级业务权限新建连接，未授权连接被拒绝。若连接只提供 CRM 授权而不提供可验证的 ChatGPT 个人身份，则表述为“仅已授权的连接”，不宣称锁定某个 ChatGPT 账号。 |

每一步先在合成记录上验证允许和拒绝两面，再部署对应路径。首台设备验证失败时保留申请页和后台审批，不对所有用户启用全站拦截；出现问题不以恢复已知的匿名 Person 读取作为回滚办法。

## 首台申请故障和修正（2026-11-10）

用户反馈点击申请后只看到通用错误。两名生产成员的认证 UID 与名单一致，调查时没有待审/批准记录。旧实现把登记错误折叠为人物服务的通用错误，不能从历史日志确定这台 iPad 的原始错误原因。

发布修正：person_360 使用其现有服务端凭据和限定为 public 的专用登记 RPC；服务端从 CloudBase 运行时取 UID。新增 RPC 仅 service_role 可执行，不增加表写权限，也不提供批准/撤销操作。原后台审批及其他业务接口不变。前端区分本地密钥存储、账号未登记、会话失效和登记服务故障。批准后，请回到相同浏览器再次点击申请，看到“设备签名验证通过”才算首台真机试点通过。这个检查不读取业务数据。

验证：生产迁移历史及三种角色的实际执行权限已核对。独立普通账号用真实浏览器登录，同一入口修正前只返回人物通用错误，修正后明确返回 DEVICE_MEMBER_REQUIRED，未产生设备；测试账号随后已停用。隔离数据库验证启用成员只能申请 pending、未批准不能领取挑战、浏览器角色不能直调新 RPC、服务角色不能批准，以及回滚保留设备记录。生产的真实成员申请、后台批准、iPad 签名验证不由自动测试代做。
