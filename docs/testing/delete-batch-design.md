# 客户与候选人删除批次设计

基线：05cf56aff8e746183ea63ca67d641833f32859bd / release-20260922-151500。
范围：仅 public；不操作 pr 或 pr_ 云函数。

## 已确认根因

customers.remove 只删除当前活动状态的客户、6 类直接子记录、活动候选人及其跟进；同一次调用写相同 deleted_at，但各个请求不在一个事务中。候选人更新的一处返回错误还未被检查。

customers.restore 没有读取父记录删除信息，按 customer_id/candidate_id 清除所有删除标记，也会恢复原先独立删除的候选人及其跟进。对已恢复的客户再次调用也会继续清除子记录删除标记。

recruit_candidates.remove 只标记活动候选人与活动跟进；restore 只检查客户是否仍删除，随后无批次限制地恢复全部增员跟进，已活动候选人也可能被再次计入恢复。

两个 trashList 统计的是所属全部已删除子记录，而非这一次删除实际可恢复的记录。

真实列复核：customers、followups、gifts、photos、policy_review_reports、ocr_records、products、recruit_candidates、recruit_followups 共 9 表均无 delete_batch_id。customers.deleted_at 是 timestamp without time zone，其余为 timestamp with time zone；不可把历史时间字符串相同作为可靠批次证明。

单独删除 followups/gifts/photos/recruit_followups 等子记录仍为硬删除；本方案不改变它们的删除语义，也不能恢复已经不存在的记录。

## 新删除语义

1. 每次成功删除一个客户或一个候选人生成一个 UUID 批次。同一事务内，只对本次由活动变为删除的记录同时写 deleted_at 与 delete_batch_id。
2. 删除客户：本次标记的直接子记录、候选人及候选人跟进继承客户批次。此前已经删除的候选人及其子记录不改时间、不改批次。
3. 单独删除候选人：候选人与本次活动增员跟进共用新的批次。
4. 恢复只处理所选根记录的批次，且同时限定父子归属关系和 deleted_at 非空；清除本次恢复记录的两个标记。不同批次、历史无批次记录和已硬删除记录不恢复。
5. 重复恢复活动根记录返回 restored=0，不扫描恢复其子记录。候选人的客户缺失或仍删除时跳过，保持“先恢复客户”的规则。
6. 删除/恢复通过限定 public 的数据库事务执行，固定父→候选人顺序锁定根记录，避免部分失败导致跨请求半删除。云函数仍为原 callFn 的业务入口，API 保留 ok/restored/cascaded/skipped 等字段。

## 历史兼容（已确认）

不按时间、同客户或临近时间自动回填历史批次。无批次根记录只恢复自身，其他删除标记保持原状；客户恢复后，历史独立候选人仍留在候选人回收站，可由用户单独选择恢复。

回收站入口、列表分页、批量/单项恢复保留。恢复提示明确说明“历史关联记录未自动恢复”，避免成功提示让用户误以为全部子记录恢复。计数与本次可恢复批次匹配，不将历史独立删除记录算入自动恢复数量。历史子记录的进一步恢复需单独核实与明确选择，不在本包猜测处理。

## 迁移、权限与视图

- 9 表增加可空 UUID delete_batch_id，无默认值，不回填历史数据；按关联条件检查必要索引。
- 数据库事务入口仅授予现有受信服务器通道所需角色，撤销默认 PUBLIC/authenticated 执行权限；不引入 SECURITY DEFINER 越权通道，保持此前 RLS 修复。
- 检查受影响视图和依赖；如回收站查询需要新增列，显式维护对应视图列与 security_invoker=true、原有效授权。不得为了补列恢复 authenticated 的旧授权；不使用 CASCADE。
- migration 与 rollback 配对。回滚必须先检查未恢复批次，存在批次数据时拒绝直接丢弃列，避免永久失去归属证据；采用安全的分阶段回滚并说明代码部署顺序。不能把旧“恢复全部子记录”的风险静默带回。
- 在代码改变前完成必要兼容确认；本设计文档不是已执行迁移。

## 验证清单

- 单独硬删除子记录，再删除/恢复客户，该子记录始终不存在。
- 历史独立软删除子记录、候选人、增员跟进均不会被客户恢复带回。
- 新删除客户的活动子记录与候选人链共享批次；只恢复该批次。
- 单独删除/恢复候选人，只恢复本批次跟进。
- 无批次历史客户/候选人仅恢复自身，并给出兼容提示。
- 同一对象多轮删除/恢复、重复请求、混合批量、父客户已删除、缺失父客户。
- 同一时间不同批次不能相互恢复；并发与中途失败保持事务一致性。
- 回收站列表、计数、单项/批量恢复交互与相邻旧功能回归。
- 所有写测试使用明确标记的隔离记录；不删除或重写真实业务记录。

## 实施状态

用户已确认历史无批次记录采用保守恢复规则。迁移 `20260922080000_delete_batches` 已应用到生产 `public`；`customers` 与 `recruit_candidates` 云函数改为调用 `public.crm_delete_batch`，回收站页面显示精确可恢复计数和历史记录提示。

依赖检查确认现有视图使用显式列清单；批次字段由云函数直接读取基表，页面及既有视图契约不需要该字段，因此没有重建视图。`v_recruit_candidates` 与 `v_recruit_candidates_trash` 的 `security_invoker=true` 保持不变。

配套回滚为数据保留型运维回滚：保留批次列与安全恢复能力，暂停新删除，避免丢失已经写入的批次证据或重新引入恢复全部历史子记录的问题。
