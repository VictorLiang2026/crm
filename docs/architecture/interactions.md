# Person interactions V1

`public.interactions` is an additive Person-level ledger. It does not replace or copy `public.followups`, `public.recruit_followups`, or `public.activity_participants`. Its first writer is manual capture; `source_type='manual'`, `source_id=NULL`, and `created_by_uid` records the authenticated actor. An optional `activity_id` links an existing, active activity. `importance` is 1–5 with default 3. `person_id` and `activity_id` use restrictive foreign keys; a unique `(source_type, source_id)` index protects future source materialization from duplicate imports.

`InteractionService.listForPerson()` reads a bounded number of direct ledger rows and existing source rows, normalizes them into one timeline, and de-duplicates any source that has later been materialized. It maps customers through `persons.legacy_customer_id`, recruit followups through `recruit_candidates.customer_id`, and activity participation through customer/recruit IDs or a speaker explicitly linked to that customer/candidate. Only `attended` participants of active activities count as interactions. Unlinked or ambiguous speakers are not guessed into a Person. Deleted source rows and deleted Persons are excluded. Date-only legacy events are interpreted as China local dates; manual capture requires a timezone-qualified timestamp. The default response limit is 20, maximum 50, with bounded source reads. This is a recent timeline, not a complete historical export.

The ledger is protected by forced RLS and a `service_role` policy. `anon` and `authenticated` receive no table privileges. The service must be called only behind a real CloudBase login check and a server-side database credential; the browser never receives that credential. The current Legacy Quick Capture and followup CRUD paths remain unchanged. No old rows are backfilled, so existing deletions, edits, and restores remain governed by their original tables. Manual ledger records have no V1 edit or delete API.

The existing `person_360` Event Function exposes two additive actions behind its existing `getUserInfo()` guard: `listInteractions` accepts `{personId, limit?}` and returns `{rows, limit, hasMore}`; `createInteraction` accepts `{personId, data}` and returns `{interaction}`. `data` includes `interaction_type`, a timezone-qualified `interaction_at`, nonempty `summary`, and optional `channel`, `raw_note`, `activity_id`, `importance`. The function fixes `source_type='manual'`, `source_id=NULL`, and the actor UID server-side; callers cannot choose a legacy source or its ID. The function reads legacy tables only and uses its existing server-only PG API credential. No frontend route or old action changed.

Migration: `cloudbase/migrations/20260926213135_interactions.sql`. Rollback: `cloudbase/rollbacks/20260926213135_interactions.sql`, which refuses to drop a nonempty ledger. The migration is additive, touches only `public`, and does not rebuild any existing view because no existing base table was altered.
