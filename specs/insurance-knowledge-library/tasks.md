# 保险业务资料库与双建议功能开发计划

## 1. 计划目标

为单人保险代理人 CRM 建设可审核、可追溯的业务资料库，并把它直接接入客户 AI 跟进建议。每次生成后**同时展示两条可选建议**，由用户选择其一：

1. **行业与客户策略建议**：使用有来源和复核日期的国际/行业实践、经授权的代理人经验和 Playbook，结合该客户已记录的事实，形成销售方法、沟通逻辑、澄清问题和下一步。
2. **资料库参考建议**：使用同一份客户事实，重点检索公司产品、服务、政策、案例、沙龙、绩优分享等已审核资料，形成更贴近现有资料依据的建议，并逐条展示引用。

两条建议必须在同一结果页同时可见，不得用 Tab 隐藏其中一条。用户选择只记录其选择，不等于已联系客户，也不自动写入业务记录。

保险行业公开材料支持循序渐进、带人工监督和引用的做法。EIOPA 的调查报告指出，生成式 AI 已广泛试用，但多数用例仍处概念验证阶段，人工监督仍占主导；Zurich 的公开概念验证结合指南检索与相似案例，但仍要求生产级验证。[EIOPA 调查](https://www.eiopa.europa.eu/publications/generative-ai-market-survey-outlook-use-cases-and-risk-management_en)、[Zurich 保险工作流概念验证](https://www.zurich.com/about-us/ai-at-zurich/ai-driven-underwriting-workflow)。消费者研究也强调保险 AI 输出的准确、透明和数据保护。[Geneva Association 研究](https://www.genevaassociation.org/publication/digital-ai-transformation/gen-ai-insurance-customer-journey-0)

## 2. 固定设计决策

### 两条建议共用与区分的上下文

- **共用**：同一客户的已确认 CRM 事实、近期相关互动、当前机会阶段；不可将推断当成客户事实。
- **行业与客户策略建议**：检索 `industry`、`top_performer_sharing`、`playbook` 和适用的去标识案例；只将有来源/复核日期的条目称为“当前行业依据”。模型通用推理如使用，应标为“通用策略推理”，不可伪称引用了最新研究。
- **资料库参考建议**：重点检索有效的公司产品、服务、招募政策、活动规则、沙龙模板及相关已确认案例/分享；不能让模型创造未在资料中出现的产品或政策事实。
- 两组各自有服务端来源 allowlist，验证知识状态、日期、适用地区和引用 ID。两条都可以没有资料引用，但必须明确标注“无资料库依据”。
- 初始实现尝试一次 AI Gateway 运行返回两项结构化候选，以共享同一客户快照并限制额外复杂度；须在 WP0 验证当前 Gateway/Registry/`ai_results` 契约是否支持。若不支持或两类上下文互相污染，WP0 需报告并提出最小改动方案，不得在后续包静默改成双模型/双调用。

### 用户选择

- 返回和保存两条完整候选，不默认选中其中一条，不因“推荐”标签替用户选择。
- 页面两个建议面板同时展示：名称、核心逻辑、澄清问题、下一步、注意事项、来源和来源日期。
- 用户点击“选择此建议”后，Runtime 记录被选候选及可选修订；另一候选仍留在历史中。
- 选择不会创建跟进、Action、Opportunity、活动、客户字段更新或外发消息。未来要执行仍走 `Command → Plan → 服务端 Preview → 人工 Confirm → 有范围授权 Execute`。

### 资料与内容边界

- 使用现有 `public.knowledge_items`、`public.playbooks`、AI Runtime。业务域优先存 `knowledge_items.metadata.domain`，不擅自扩展 `item_type` 约束。
- 原件私有保存；浏览器数据仍经 `callFn`，不新增浏览器端 `app.rdb()` / `app.storage` 写入。
- 单人由本人确认草稿，不增加多人审批。客户隐私不进入共用资料库。
- 健康/财富沙龙为可复用模板，具体活动沿用现有 `activities` 和相关表。
- 绩优分享必须记录授权/匿名、背景、时间段、结果口径和局限；个案不得被写成保证业绩或普遍因果。
- 模型选择经 AI Gateway / CloudBase 配置，不硬编码厂商或具体模型。
- 所有新 UI 在 `crm/js/modules/console/`，按 iPad 设计，通过 `i18n.js` 与 `t(key)` 提供简中/英文。

## 3. 依赖与顺序

```text
WP0 只读基线与接口核查
  └─ WP1 知识数据/来源模型
       └─ WP2 单人资料摄取与治理
             └─ WP2A 国际行业知识初始集
                  └─ WP3 检索和双来源上下文
                       └─ WP4 双建议 Gateway/服务端契约
                            └─ WP5 同屏展示、选择与历史
                                 └─ WP6 评估、真实资料试用与发布验收
```

每个包都独立检查本地差异，按项目规则完成必要语法/回归、精确部署、Git 提交推送、发布标签和三端核对。跨模块包必须记录 regression 结果。任何会改变现有 AI 建议行为的包，在写相关代码前先说明影响、兼容方案和回归范围，取得用户明确确认。

检查：

5. 核对活动页已经支持的沙龙活动与活动主题对象、Person/招募 AI 相关页面，确认本期应接入的位置。

**交付门槛：**基线一致且双候选落库契约清楚后再进入 WP1；如有差异，先解释差异来源并停止后续修改。

### WP1 — 资料来源与双建议数据契约

```text
任务：依据已确认的保险资料库详细设计，为单人 CRM 建立最小资料来源数据底座。先完成影响说明与 migration/rollback 设计，等待用户对任何影响已有行为的范围明确确认后再写代码或执行数据库迁移。

范围：只操作生产 CloudBase crm-d1gkae8ddc930d151 的 public schema；不得访问 pr schema 或 pr_* 函数。复用 knowledge_items、playbooks、ai_tasks、ai_runs、ai_results；不得删除/重命名旧对象，不改变旧建议默认行为。

实现内容：
1. 根据 WP0 的只读事实，决定是否新增最小 knowledge_sources 登记对象；登记标题、domain、来源、地区/辖区、发布日期、生效/失效/复核日期、私有文件键、文件类型/大小/hash、提取状态、版本关系和创建/更新时间。若现有对象/metadata 能可靠承载其中一部分，避免重复存储。
2. 为 knowledge_items 的来源文件关联和页码/章节定位选择唯一事实源（优先明确 FK/locator；若确有理由使用 metadata，则制定稳定契约，不并存两套真相）。
3. domain 覆盖 product/company/service/recruitment/industry/campaign/health_wealth_seminar/top_performer_sharing/legal_tax/case/playbook；保留现有 item_type CHECK 值，首期用 metadata.domain 细分。
4. 定义双建议候选和选择契约：同一 customer subject/context snapshot 下保存 strategy_based 与 library_based 两项；分别保存允许的 source refs、来源版本、候选顺序、用户选择/编辑。按 WP0 结果优先复用 ai_results 字段，不足才提出最小加法 schema。用户选择不代表执行了业务动作。
5. 角色权限最小化：敏感快照只由 service_role/现有服务端边界访问；表开启并强制 RLS；不授予浏览器直连权限。
6. 为每个新数据库变更提交 public 限定 migration 和保护已有数据的 rollback；rollback 有数据/引用时拒绝删除。检查并重建受影响视图（如无视图依赖也记录证据）。

数据库变更执行前必须重新核对当前线上 public 元数据、迁移历史及依赖；不得使用猜测的 search_path。按项目规定做针对性回归、安全门槛、精确发布、提交/推送/标签和发布后 sync-check。任何新表/字段的权限或 AI 结果行为变更需先给用户看影响说明并确认。
```

**验收：**原始知识可追溯到版本/定位；两个建议候选可在同一个客户任务下分别保存、单独选择；旧 ai_recommendations 与历史数据读法不变。

### WP2 — 单人资料上传、整理与确认

```text
任务：为 Console 知识与话术页新增单人资料摄取与治理流程。仅按 WP0/WP1 已确认的对象与权限实现；开工前先列出精确页面、函数、表/Storage、请求大小、兼容和回归影响。不得把 Person 文件导入流程改造成知识上传。

资料包括公司产品、公司/服务介绍、招募政策、行业/国际实践、竞赛、健康和财富沙龙模板、绩优分享、法务税务资料与案例。首期支持经验证可安全提取的 PDF、DOCX、TXT；无法解析/加密/扫描件清楚提示，不假称已学习。

实现：
1. 在 crm/js/modules/console/knowledge-governance.js 和 data.js 扩展现有 #/knowledge-governance 页面；i18n.js 通过 t(key) 增加中英文字典，简中默认，iPad 布局。
2. 通过 callFn 完成上传/登记、提取、重试、草稿查看、本人确认、修订、过期/停用；禁止新增浏览器端 app.rdb()/app.storage 写入。
3. 原文件及全文使用私有存储和服务端操作；不复用 recruit 存储路径、不返回公开 URL。依据 WP0 核实的 Cloud Function payload 限制制定明确大小上限；如果需要绕开 callFn 的浏览器直传才可支持常用文件，停止并报告，不能自行突破项目约定。
4. AI 提炼摘要、知识点、营销/沙龙大纲、绩优分享条目仅保存草稿。只有唯一用户确认后才可检索；按钮需核对服务端会话身份和预期版本，不信任客户端 confirmed。
5. 绩优分享表单支持匿名/署名与授权状态、分享时间段、背景、行动方法、结果指标定义/来源、可迁移点和限制。缺授权、含客户识别/健康/保单资料时阻止确认并提示去标识。不得上传或种入生产真实个人内容作为测试。
6. 沙龙模板字段覆盖 health/wealth、目标受众、教育目标、时长、议程、互动问题、主持提示、产品引用、跟进建议和边界。只提供查看/复制，不改 activities 页面或单场活动记录。
7. 行业/法务税务条目需来源、地区和日期；缺失时可以是草稿，不能作为当前有效规则检索。
8. 资料列表显示“复核日期已到”提示；提示不自动确认或覆盖资料。`valid_to` 到期时必须从当前建议检索中排除，但保留历史版本与引用。

只增加明确必要的文件、函数和 public migration；共享云函数副本逐个同步。做文件解析边界、权限、双语 iPad、旧知识治理与活动入口回归。对跨模块或改变现有知识流的改动，编码前先提交影响说明并取得用户明确确认。按项目发布规则部署明确静态文件/函数、提交推送打标签并核对云端一致。
```

**验收：**草稿从未进入模型上下文；原件/提取文本私有；过期条目可保留历史但不进入当前检索；本人可确认/修订/停用；活动数据不被复制到知识条目。

### WP2A — 国际行业知识初始集与来源维护

```text
任务：为“行业与客户策略建议”准备一组小而可靠、可复核的国际保险行业知识卡草稿。此包主要是研究/内容整理，不修改 CRM 代码、不写生产数据库、不部署、不代替用户确认资料。

使用官方监管机构、国际保险组织/行业协会、公开研究和具名保险机构公开材料。优先涵盖：客户旅程与需求沟通、信任/透明/人工服务、持续服务与客户关系、保险分销/代理人能力、营销沟通、招募与代理人发展。每条总结都需给来源 URL、发布者、发布日期/研究期间、适用地域、复核日期、可迁移原则、不可直接外推的边界；区分法规/监管依据、行业调查和单一机构案例。不得把欧洲/美国/其他市场规定写成 CRM 使用者所在地的规则。

交付：
1. 先研究并列出建议来源清单及为何可信；大约 8–15 条高价值知识卡即可，不为数量收集资料。
2. 每张知识卡用中文总结、标记 `metadata.domain=industry`，并包含 `source_date`、地区、复核建议日期和适用场景。英文标题/短摘要可并存，但避免整段复制受版权保护的原文。
3. 给出映射到 strategy_based 建议的主题标签：needs_discovery、objection_handling、customer_trust、relationship_service、ethical_marketing、agent_development 等；不得包含产品政策事实。
4. 将内容写成可导入/可手工录入的草稿文件和来源目录，状态为 draft；不通过 CloudBase CLI/MCP 写生产知识库。用户本人在知识治理页审阅后再确认。
5. 说明资料更新机制：到复核日期后 UI 标“需复核”，过期法规/行业结论停止作为“当前”依据；没有新的来源时保留历史但明确日期。

只用公开可引用来源，核对页面当前可访问与发布日期；精简转述、逐条列出处。把未核实、地区不明或营销宣传性材料排除或明确标低可信。交付草稿、来源清单、版权/适用范围注意事项和未覆盖主题，不扩写到本地产品/税务结论。
```

**验收：**行业建议上下文有可追溯、带日期和地区的初始来源；没确认的知识卡不进入模型；来源失效/过期能降级或退出“当前行业依据”。绩优分享实际内容由用户提供和授权，不由 Codex 臆造或从个案推演。

### WP3 — 双来源检索与可验证上下文

```text
任务：实现资料库的服务端检索与双建议上下文构建，作为单独工作包；此包不改客户建议页面和旧 ai_recommend 业务行为。

先读本地 AI Gateway/skill registry/context engine、知识治理服务及 WP0/WP1/WP2 证据。改动前列出影响范围并取得适用的用户确认。只操作 public，不依赖 pr/pr_*。

检索组 A（strategy_based）：已确认、当前有效的 industry、top_performer_sharing、playbook、适用的 case/story；包含来源日期、地域、适用范围、授权/匿名状态及可迁移边界。
检索组 B（library_based）：已确认、当前有效且适用地区匹配的 product/company/service/policy/recruitment/campaign/health_wealth_seminar/legal_tax/case/playbook；只传与客户销售场景有关的必要片段。
两组共享同一份有界、可追溯的 customer context snapshot；不要在检索中把客户事实写回知识库。

实现要求：
1. 先用 domain、verified/lifecycle_status、valid_from/valid_to、jurisdiction、关键词/全文和上限完成 V1；首期不新增向量库/embedding provider。
2. 为两个上下文生成独立的引用 allowlist；服务端过滤超期、未确认、未生效、地区不符、未获分享授权或引用失效内容。
3. 每个片段携带 public schema/table/id/version/来源名/日期/locator；限制条数、字符数和重复来源。
4. 输出输入快照要精确记录实际送入模型的 A/B 证据与客户字段，能在 AI 历史审计中解释“为什么得到这两条”。不泄漏另一个客户资料。
5. 准备 30–50 条代表性问题的离线检索用例；测试有效/过期产品、政策、沙龙与绩优分享、跨地区法务资料、无匹配问题和未核验草稿。
6. 只加必要测试/工具，不用真实客户数据做破坏性操作。若检索约束需要 schema 变更，必须再提供 migration/rollback 并重新走用户确认。

交付检索模块、来源 allowlist 验证、测试报告和上下文契约文档；按项目完整回归与发布规则完成发布。此包不修改 ai_recommend/recruit_recommend 的调用。
```

**验收：**未核验/过期/地区不符的来源在模型调用前被过滤；模型不能通过伪造 ID 绕过来源 allowlist；没有来源时上下文明确无匹配；A/B 上下文不串用。

### WP4 — AI 同时生成两条建议

```text
任务：在 AI Gateway 中为客户跟进提供“双建议”生成能力。同一客户、同一输入和同一 customer context snapshot，每次都产生 strategy_based 与 library_based 两个独立候选；不得只生成一个混合建议后在 UI 拆成两栏。

开工前重新读取 WP0 baseline、WP3 检索契约和当前 AI Gateway/Registry/ai_results 实现。先把对现有客户 AI 建议行为的影响、兼容方案、函数/Skill/数据库范围、回归清单告诉用户；取得明确确认后才能改代码。

建议契约：
- `strategy_based`: 以销售逻辑、国际/行业经验及经授权绩优方法为重点，并结合此客户已核实上下文；明确区分有引用的行业材料和通用推理。
- `library_based`: 以当前匹配的公司资料为重点，针对同一客户形成更贴近已审核资料的下一步；产品/政策事实必须来自有效知识引用。
- 每条候选分别返回摘要、判断逻辑、待澄清问题、建议动作/沟通草稿、边界提示、source refs 与 match status。
- 不足以生成时也返回结构有效的候选，说明缺什么信息/依据；不得伪造来源或把推断写为事实。
- 绩优分享是个案启发，不承诺复制结果；健康/财富/法务税务约束沿用设计。

优先使用一个 Gateway task/run 生成两个结构化候选，以减少成本并保持客户快照一致；各候选仍需分别做 schema 和来源白名单复核。若同一 run 写两条 ai_results 不符合现有约束，按 WP0 用户已确认的最小适配方案实现，不能更改旧 Runtime 默认路径。生成只写 AI Runtime 审计，不写客户、跟进、机会、行动、活动、招募或产品数据。

新增独立 Skill/契约或明确版本，模型选择继续由 AI Gateway/CloudBase 配置，不硬编码具体模型/厂商。保持旧 ai_recommendions DTO、函数入参和历史记录兼容；不要顺手重构 ai_recommend/recruit_recommend。完成 schema/引用/失败/超时/两候选同一客户快照的离线测试与相邻旧 AI 回归，按项目精确部署、发布和三端核验。
```

**验收：**每次成功请求有且只有一个 strategy_based 与一个 library_based 候选；任一候选失败/无证据不得被另一候选伪装替代；两个候选可独立溯源；没有业务数据副作用。

### WP5 — 同屏展示、用户选择和历史记录

```text
任务：将 WP4 双建议接入核实后的当前客户建议入口。两条建议必须同时展示，用户明确选择其中一条；本包不生成新产品推荐执行器，不创建业务记录。

实现前复核实际页面调用链并说明影响/兼容/回归，取得用户对已有建议交互变更的明确确认。不得删除旧建议历史或旧 URL。

UI：
1. 在用户当前客户跟进建议入口展示两个同时可见的建议面板：A“行业与客户策略”、B“资料库参考”。iPad 横屏可并排，窄 iPad 宽度顺序纵排；不使用隐藏式 Tab 或默认自动选择。
2. 每张卡显示要点、销售逻辑、澄清问题、下一步、注意事项、来源名称/日期和可打开的资料引用；strategy 卡注明通用推理与引用依据的区别，library 卡突出匹配到的知识。
3. 两条建议都有独立的“选择此建议”。选择后仅该候选标记 user_selected；另一条保留为未选，选后可选补充/修改并记录 user_edited/final result。
4. 页面清楚提示“选择表示采用此建议作为工作参考，不表示已联系客户或执行动作”；若后续要生成跟进记录，保持现有独立用户操作与安全 Preview/Confirm 语义。
5. AI 历史保留同一次任务的两条建议、所引用资料版本、用户选项和编辑痕迹；从引用可跳回知识治理详情。旧 `ai_recommendations` 历史继续可查看。
6. 所有文字走 i18n/t(key)，中英文齐全；遵守 iPad only、新 AI-native 模块放 crm/js/modules/console、复用组件/CSS 规范。

回归覆盖新建/失败/重试/双卡显示/分别选择/修改后选择/刷新回看/引用跳转/无来源/过期来源；并核查旧客户建议入口、Person 详情、AI 历史、登录与相邻跟进流程。禁止直接更新客户或跟进表。只部署明确的模块/CSS/函数文件，按项目发布流程提交、打标签并核对一致。
```

**验收：**两条始终同时可见、用户明确选其一；只记录选择，不误报为执行；历史保留两条和版本化引用；旧历史兼容。

### WP6 — 资料集评估、单人试用与最终验收

```text
任务：对资料库与双建议做最后的质量、隐私和兼容验收。只使用用户授权材料、公开可引用来源及隔离合成记录；不以真实客户进行破坏性测试、不在用户未授权时写入生产知识库。

评估集至少 30 个配对场景，覆盖：客户需求澄清/异议/下一步；产品与服务事实；招募；健康/财富沙龙；绩优经验适用条件；法规税务地区与日期；过期资料；无资料匹配；客户上下文不足。

每题记录：A/B 是否都生成且不同、同一客户快照是否一致、策略依据和资料库依据是否分清、引用是否真实有效、地区/有效期是否正确、是否有编造产品/医疗/税务/收益/绩优成功保证、用户选择是否仅标记结果、业务记录是否保持不变。

必须满足：
- 引用真实性与授权过滤 100%（任一伪造/越权/过期引用均阻止发布）。
- 成功请求恰好两条建议，失败请求清楚说明原因，无默认选择。
- 选择候选后只有该候选标记 selected；历史可重放到当时版本。
- 关键旧功能 regression 通过；任何失败都停止最终发布并修复。
- 保存评估报告、未覆盖项、单人试用指引、回滚/恢复办法和发布证据。

如果评估发现需要改变建议生成或活动/招募流程，先报告影响范围、兼容方式和回归范围并取得用户明确确认，再另开包；不得扩张本次验收范围。依项目发布要求完成最终精确部署、Git 发布标签、CloudBase/GitHub/本地一致性核对和发布后线上验证。未执行的真实 AI/登录/业务链路要明确列为未验证，不得以源码哈希代替。
```

**验收：**质量报告可复核，已知风险可定位，未验证项明列；达到门槛后用户可在实际客户建议流程中对比并选择两条建议。

## 5. 交付顺序建议

优先做 WP0 → WP1 → WP2 → WP2A → WP3 → WP4 → WP5 → WP6。WP0 是实施前审计，完成后若线上基线/接口差异影响设计，先更新本计划并再次确认。WP2 与 WP3 不改变旧建议行为；WP4/WP5 直接改变客户建议体验，必须在编码前得到用户明确批准。WP2A 的行业知识保持草稿，最终是否入库由用户本人确认。

## 6. 明确不在本计划内

- 自动向客户发消息、自动新增跟进/Action/Opportunity。
- 自动推荐或确认购买某个具体保险产品。
- 实时爬取互联网并把结果直接当作已核验行业知识。
- 未经授权处理绩优分享人的身份/客户案例，或以分享结果建立代理人排行榜。
- 先建 embedding/vector 设施；只有检索评估证明关键词/全文不足时再单独规划。
- 改造现有活动工作流、多人协作权限、手机页面或 `admin.html` 旧业务实现。
