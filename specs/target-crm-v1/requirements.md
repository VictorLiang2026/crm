# 目标 CRM：后续开发需求与验收标准

状态：规划中；2026-10-02。依据《CRM按步骤设计文档》及当日线上 `public`、代码、页面盘点。本文件是目标与验收契约，不表示所列能力已上线。

## 目标与边界

系统以 Person 为身份入口，以 Interaction、Context、Relationship 为事实脉络，以 Opportunity、Action、Commitment 为执行对象，以 Outcome、Learning 为反馈闭环。AI 负责提取候选、解释和建议；数据库负责事实与筛选；关键业务影响由人确认。主导航使用已上线的“今日 / AI助手 / 人 / 机会 / 活动 / 招募 / 更多”，全局保留快速记录。新入口逐步取代旧入口的日常使用；旧功能在有证据证明完整替代前仍可从“更多”和旧 URL 操作。

只在当前 CRM 和 `public` schema 内迭代；不访问或依赖 `pr` / `pr_*`。不另建一套 CRM，不整体重写 `admin.html`，不增加模型选择后台。CloudBase 托管模型及套餐资源点是现阶段模型运行与结算方案；业务代码只依赖 AI Gateway 的能力接口。

## 用户故事与可验收要求

| ID | 可验收要求 |
| --- | --- |
| R01 身份 | 当用户新建或关联 Person 时，系统必须先以 `PersonService.resolveName()` 查找；唯一候选需人确认，多候选需人选择或补充限定；AI 不得自动认定身份。活动客户、招募候选人与嘉宾的明确关联应可追溯到同一 Person。 |
| R02 Person 360 | 当用户打开 Person 360，系统应在一个主入口展示身份与角色、关系/家庭、带来源的近期互动、Fact/Signal/Inference、机会、行动、承诺及适用的保险、招募、活动信息；每块均能跳到其完整操作入口。 |
| R03 快速记录 | 当用户提交原始记录，Quick Capture V2 应先解析为互动/事实/信号/机会/行动/承诺候选，展示身份与逐项预览；只有用户确认的项目才通过服务端核实写入。重复确认不得产生重复业务记录。 |
| R04 执行闭环 | 当行动或承诺到期、完成或过期，Today 与 Person 360 应显示同一条事实，允许适用的人工更新，并保留来源、状态及完成时间；旧行动来源仍由兼容视图可见但不重复。 |
| R05 机会闭环 | 当证据提示潜在机会，系统可生成带来源的 Opportunity Candidate；只有经过人工编辑/确认及服务端预览的候选才成为正式 Opportunity。正式机会可关联 Person，旧 customer 机会继续工作。 |
| R06 领域上下文 | 当 Person 涉及活动、招募或保险，系统应汇总相应事实、近期变化及下一步操作；不能将“报名”等同“到场”，不能将“记录中未见保险讨论”等同“从未讨论”。 |
| R07 AI 能力 | 当用户运行 Meeting Prep、Conversation Playbook、AI Search、活动复盘或 Today Brief，系统应限制上下文字段/数量、标明来源，经 AI Gateway 使用 CloudBase 配置模型；事实筛选由数据库完成，模型不能编造查询命中或未经核实的证据。 |
| R08 安全命令 | 当自然语言涉及 create/update/close/delete，系统必须按 Command → Plan → 服务端 Preview → 人工 Confirm → 有范围的 Execute 运行；未接入的对象/动作拒绝执行，确认令牌与登录身份、版本、期限绑定，一次性消费。 |
| R09 反馈学习 | 当用户接受、改选、编辑或拒绝 AI 结果，系统应记录对应 `ai_results` 反馈，并在发生实际 Outcome 后关联 Learning；第一阶段只形成可审查指标，不自动改业务规则。 |
| R10 主动提醒 | 当关系节奏、活动、承诺、机会或招募事实达到阈值，系统可生成有解释、置信度、来源和建议动作的候选提醒；不得只按固定未联系天数判断，也不得自动生成已确认事实或执行动作。 |
| R11 演示数据 | 当某链路没有可用数据，系统应通过同一 CRM 的受控种子器生成少量虚构、明确标记的记录；同版本重复运行不增加记录。用户无需手工输入即可打开预填演示场景，并经过与真实流程相同的预览和人工确认。演示数据可以保留。 |
| R12 演示隔离 | 在正常经营模式下，演示记录不得进入真实 Today 排名、经营统计、漏斗、主动提醒、AI 上下文或外发动作；在显式演示模式下可贯通同一业务服务。无法保证隔离的模块不得先注入演示数据。 |
| R13 性能与一致性 | 当客户、行动、活动数据增长时，列表和聚合应在服务端分页/限量，有关键查询索引；多步骤写入须事务或幂等保护。每次独立改动以实际查询计划、耗时和回归证明未破坏旧功能。 |
| R14 权限 | 所有新增数据访问仅限 `public`，遵守真实登录、RLS、视图调用者权限和最小授权；自动安全测试检查匿名、已登录及服务角色的允许/拒绝矩阵，不能只依赖静态源码检查。 |
| R15 Legacy 治理 | 当新入口被提议替代旧功能时，必须有逐项功能矩阵、迁移/回滚、真实使用与自动回归证据。未完全覆盖的旧入口保留在“更多”；删除或重命名任何现有表、视图、函数、路由须另获针对该项的明确批准。 |
| R16 发布 | 每个独立工作包先核对本地/GitHub/云端基线，说明现有功能影响并按 `AGENTS.md` 取得必要确认；数据库变更配 migration/rollback；通过相关回归后只发布受影响产物，提交推送、打标签并核对三端一致。 |

## 最终端到端验收场景

使用最多 6 位虚构 Person、少量家庭/客户/招募/嘉宾/活动/保单上下文及一条可信和一条不足证据，在同一线上 CRM 的显式演示模式中完成：选择人物 → 快速记录并确认身份 → 互动及 Fact/Signal 候选确认 → 机会候选确认并成为正式机会 → 生成行动和承诺 → Today 提醒 → 活动或招募跟进 → 记录行动 Outcome → 保存 AI 反馈和 Learning。每步可看到上一步 ID/来源及下一步入口；重复执行不多造数据；退出演示模式后正常经营看板不含演示数据。用真实测试账号验证登录、权限、手机页面和旧路由回归。

## 明确不做

不在本规划轮写入演示数据或改业务逻辑；不自动发送客户消息、不自动执行销售动作、不把 AI 候选直接转为已确认 Fact；不为了减少视觉重复而提前删除旧表/函数/路由；不建立新的保险大表群或模型厂商选择系统。
